# Invite link and join requests (new domain), V12

### Requirement 24: Invite Link and Join Requests

**User Story:** As a Board_Owner, I want to invite people to my Board with a link and see who asked to join, so that the right people can request access and a Manager or Admin can approve them.

Note (V12, Decision AA): the Invite_Link is a second token, separate from the Public_Link. It never grants access by itself: it only lets a signed-in Member or Supervisor ask. Only a Manager or an Admin decides.

#### Acceptance Criteria

1. [INV-01] THE Backend SHALL store a nullable, unique `invite_token` on each Board (at least 256 bits from a cryptographically secure source, `secrets.token_urlsafe(32)`), where null means invites are off, and SHALL keep it out of every Activity_Log `metadata`, every log line, and every response other than the invite management endpoints of criteria 2 to 4 (Decision AA).
2. [INV-02] WHEN the Board_Owner, a Manager, or an Admin calls `POST /api/boards/{id}/invite` while invites are off, THE Backend SHALL generate and store an `invite_token`, write one `board.invite_enabled` Activity_Log row, and return HTTP 200 with `{ "enabled": true, "token": string, "path": "/invite/<token>" }`; WHILE invites are on, THE Backend SHALL return the existing token and write no row.
3. [INV-03] WHEN the Board_Owner, a Manager, or an Admin calls `POST /api/boards/{id}/invite/regenerate`, THE Backend SHALL replace the `invite_token`, write one `board.invite_regenerated` row, and make the previous link stop working at once; WHEN they call `DELETE /api/boards/{id}/invite`, THE Backend SHALL set `invite_token` to null, write one `board.invite_disabled` row when invites were on, and return HTTP 200 in either case.
4. [INV-04] WHEN the Board_Owner, a Manager, or an Admin calls `GET /api/boards/{id}/invite`, THE Backend SHALL return `{ "enabled": boolean, "token": string or null, "path": string or null }`.
5. [INV-05] IF any other signed-in user calls an endpoint of criteria 2 to 4, THEN THE Backend SHALL return HTTP 403, or HTTP 401 when no Token is present.
6. [INV-06] WHEN a signed-in user calls `GET /api/invite/{token}` with a current `invite_token` of a non-soft-deleted Board, THE Backend SHALL return HTTP 200 with `{ "board": { "id", "name", "description" }, "state": string, "request": { "id", "status" } or null }`, where `state` is `staff` for a Manager or an Admin, `member` for the Board_Owner or a BoardMember, `pending` when the user has a pending BoardJoinRequest, and `can_request` otherwise.
7. [INV-07] IF `GET /api/invite/{token}` or `POST /api/invite/{token}/requests` carries no Token, THEN THE Backend SHALL return HTTP 401, and IF the token is unknown, was disabled or replaced, or belongs to a soft-deleted Board, THEN THE Backend SHALL return the same HTTP 404 `NOT_FOUND` response in every case.
8. [INV-08] WHEN a signed-in Member or Supervisor who is neither the Board_Owner nor a BoardMember and has no pending request calls `POST /api/invite/{token}/requests`, THE Backend SHALL create a BoardJoinRequest with status `pending`, write one `board.join_requested` Activity_Log row, create one `board_join_requested` Notification for the Board_Owner and for every Manager and Admin in the same transaction, and return HTTP 201 with `{ "id", "board_id", "status", "created_at" }`.
9. [INV-09] IF a Manager or an Admin calls `POST /api/invite/{token}/requests`, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and `error.details.role`, and create no row.
10. [INV-10] IF the caller is the Board_Owner or a BoardMember, or already has a pending request for that Board, THEN `POST /api/invite/{token}/requests` SHALL return HTTP 409 with the code `CONFLICT` and `error.details.board`, and create no row.
11. [INV-11] THE Backend SHALL enforce at most one `pending` BoardJoinRequest per `(board_id, user_id)` by a partial unique index, and SHALL map a violation raised by two simultaneous requests to the HTTP 409 of criterion 10.
12. [INV-12] WHEN a rejected requester calls `POST /api/invite/{token}/requests` again, THE Backend SHALL create a new `pending` request with no cooldown and leave the earlier rejected row unchanged.
13. [INV-13] WHEN the Board_Owner, a Manager, or an Admin calls `GET /api/boards/{id}/join-requests`, THE Backend SHALL return the `pending` requests of that Board, oldest first, each with `id`, `status`, `created_at`, and `user` as `{ id, full_name, username, email, avatar_url }` (the Email is returned only to the Board_Owner, a Manager, and an Admin, which are the only roles allowed to call this endpoint; Decisions M and S as amended in V12 round 2); the optional `?status=pending|approved|rejected|all` query SHALL select another set; any other signed-in user SHALL receive HTTP 403, or HTTP 401 with no Token.
14. [INV-14] WHEN a Manager or an Admin calls `PATCH /api/join-requests/{id}` with `{ "status": "approved" }` on a `pending` request, THE Backend SHALL set the status, set `decided_by` to the caller, create the BoardMember for the requester (no duplicate when one exists), write one `board.member_added` Activity_Log row, create one `board_added` Notification for the requester, and return HTTP 200 with the request, all in one transaction.
15. [INV-15] WHEN a Manager or an Admin calls `PATCH /api/join-requests/{id}` with `{ "status": "rejected" }` on a `pending` request, THE Backend SHALL set the status, set `decided_by`, write one `board.join_rejected` Activity_Log row, create one `board_join_rejected` Notification for the requester, and return HTTP 200, without creating a BoardMember.
16. [INV-16] IF a user who is not a Manager or an Admin, the Board_Owner included, calls `PATCH /api/join-requests/{id}`, THEN THE Backend SHALL return HTTP 403, or HTTP 401 with no Token; IF the id is unknown THE Backend SHALL return HTTP 404; IF the request is not `pending` THE Backend SHALL return HTTP 409 with the code `CONFLICT`; IF `status` is neither `approved` nor `rejected` THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR`.
17. [INV-17] THE Backend SHALL leave pending requests pending when the Invite_Link is regenerated or disabled, because a request is a record of an action already taken.
18. [INV-18] THE Backend SHALL send `Cache-Control: private, no-store` on every `/api/invite` response, and THE Frontend SHALL send `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex` on every `/invite/{token}` page.
19. [INV-19] WHERE the viewer is the Board_Owner, a Manager, or an Admin, THE Frontend SHALL show an "Invite" button in the Board's App_Header that opens a modal with: the current state, a Generate action when invites are off, the full link with a click-to-copy control, Regenerate and Disable actions (each behind a `BaseConfirm` popover that says the old link stops working), and the list of pending join requests with the requester's Avatar_Image or Initials_Avatar, full name, Username, Email, and the request time.
20. [INV-20] WHERE the viewer is a Manager or an Admin, THE Frontend SHALL show Approve (primary) and Reject (secondary) on each pending request in the Invite modal; WHERE the viewer is the Board_Owner and not a Manager or an Admin, THE Frontend SHALL show the same list without those actions and with the note "A manager or an admin decides on requests."
21. [INV-21] WHERE the viewer can see pending requests and the Board has at least one, THE Frontend SHALL show the count as a badge on the Invite button.
22. [INV-22] WHEN a visitor without a Session_Cookie opens `/invite/{token}`, THE Frontend SHALL redirect to `/login?next=/invite/<token>`; WHEN the visitor signs in or registers there, THE Frontend SHALL return to `/invite/<token>` (Requirement 1, criteria 59 and 66).
23. [INV-23] WHILE the viewer is signed in and `state` is `can_request`, THE Frontend SHALL show the Board name, the description, and a "Request to join" button that calls `POST /api/invite/{token}/requests` and then shows "Request sent. You will get a notification when a manager or an admin decides."
24. [INV-24] WHILE `state` is `pending`, THE Frontend SHALL show "Your request is waiting for a decision." with no button; WHILE `state` is `member`, THE Frontend SHALL show "You are already a member of this board." with an Open board link; WHILE `state` is `staff`, THE Frontend SHALL show "You already have access to every board." with an Open board link.
25. [INV-25] IF the invite route answers HTTP 404, THEN THE Frontend SHALL show one page that says the invite link is not valid, without saying whether it was disabled, replaced, or never existed.
26. [INV-26] THE Backend SHALL record each BoardJoinRequest as `id`, `board_id`, `user_id`, `status` (`pending`, `approved`, or `rejected`), nullable `decided_by`, `created_at`, and `updated_at`.
27. [INV-27] THE Frontend SHALL show a requester's Email only in the pending list of the Invite modal, to the Board_Owner, a Manager, and an Admin, and SHALL show it in no Inbox row, Notification text, Activity_Log row, tooltip, `alt` text, or label (Decision S as amended in V12 round 2).
28. [INV-28] THE Backend SHALL return no Email in the response of `POST /api/invite/{token}/requests`, in the response of `PATCH /api/join-requests/{id}`, in any Notification payload, or in any Activity_Log `metadata` of the join-request actions, and SHALL read `User.email` for the pending list through the join of the request's `user_id` without copying it into `board_join_requests` (Decision S as amended in V12 round 2).
