# Testing, V12 changes

Requirement 15 criteria 29 to 35 are added, and criteria 36 to 39 in round 2 within V12.

29. [V12-T1] THE System SHALL include `pytest` tests for the access model of Requirement 22: that no `visibility` column exists and a `visibility` field is rejected or ignored as the schema defines; the Board list for an owner, a BoardMember, an unrelated Member, a Manager, and an Admin; HTTP 403 for an unrelated Member and Supervisor on every Board-scoped route; no BoardMember for a Manager or an Admin (including the role-change cleanup of ACC-06); assignee only from owner or BoardMembers (including the cleanup of ACC-10 and ACC-12); and the migration reset and abort of ACC-17 (Decision Y).
30. [V12-T2] THE System SHALL include `pytest` tests for Requirements 23 and 24: Public_Link management only by Manager and Admin (owner, Supervisor BoardMember, and Member get 403); one test per write endpoint of PUB-10 and PUB-11 (comment, edit field, attachment, subtask, archive, delete) returning 401 and 403 and changing nothing; HTTP 405 on every mutating method under `/api/shared`; the invite lifecycle (generate, regenerate, disable, old token 404); the join-request flow (request 201, Manager and Admin request 400, member and duplicate 409, simultaneous requests leave one pending row, reject then request again, approve creates one BoardMember, owner PATCH 403, decided request 409); and that no join-request create or decision response and no Notification body contains an Email or a token, and the pending list (INV-13) is the only join-request response that carries an Email (Decisions Z, AA, and S as amended in V12 round 2).
31. [V12-T3] THE System SHALL include `pytest` tests for Requirement 26 and 27: comment delete by the author (reply decrements `reply_count`, top-level deletes its replies, `n` is correct), 403 for a Manager and an Admin, 404 unknown, the `comment.deleted` row without text; the Subtask matrix of SUB-01 for each role and relationship; `progress` as 0 to 10, null without Subtasks, and 400 for a posted `progress`; and that Property 53 (reply count consistency) holds under random interleaved adds and deletes (Decisions AC and AD).
32. [V12-T4] THE System SHALL include `pytest` tests for Requirement 28: the three partial unique indexes (two board notifications with a null `card_id` on the same day are deduplicated, two different join requests both notify, a card notification is deduplicated as before), the CHECK constraint, the notification fan-out of INV-08, INV-14, INV-15, and ACC-12, and a constant query count for `GET /api/notifications` at 5 and at 50 rows (Decision AE).
33. [V12-T5] THE System SHALL include Frontend component tests for Requirement 25: no "Save changes" button; blur and Enter on the title send one `PATCH` with only `title`; no request for an unchanged value or an empty title; each chip popover sends one `PATCH` with one field; the Saving, Saved, and error-with-Retry states; closing waits for an in-flight save; the failed-field close confirmation; a response does not overwrite a field being edited; and each Subtask and Attachment call goes out at once (Decision AB).
34. [V12-T6] THE System SHALL include Frontend component tests for Requirements 24, 26, 28, and 29: the Invite modal for owner, Manager, and Admin (Approve and Reject only for Manager and Admin), the `/invite/{token}` states, the attachment and comment confirm modals (Cancel sends nothing, the reply text appears), the Inbox rows as links with the hrefs of INB-05, the unavailable-card notices, and the Profile grid classes at the 960 pixel breakpoint (Decisions AA, AC, AE, and AF).
35. [V12-T7] THE System SHALL include `vitest` tests that `frontend/proxy.ts` redirects a cookie-less `/invite/{token}` request to `/login?next=/invite/{token}` and that the Safe_Return_Path rule accepts `/invite/<43 URL-safe characters>` and still rejects `//evil.com`, `/\evil.com`, `https://evil.com`, `/other`, and `/invite` followed by `//` (Decision P as amended in V12).
36. [V12-T8] THE System SHALL include `pytest` tests for round 2 within V12: `GET /api/boards/{id}/members` returns the Board_Owner first, once, with `is_owner` true (also when the owner is a BoardMember) and no `email` by default; `include=email` adds the Email for the Board_Owner, a Manager, and an Admin and returns 403 for a Member; the candidate search never lists the owner; `DELETE /api/boards/{id}/members/{owner_id}` returns 404 for an owner who is not a BoardMember; `GET /api/boards/{id}/join-requests` carries `email` for the Board_Owner, a Manager, and an Admin, returns 403 for a Member and for a Supervisor who is only a BoardMember, and 401 without a Token; and no Email appears in the create or decision responses, Notification bodies, Activity_Log `metadata`, Comment bodies, or any `/api/shared` payload (Decisions M and S; ACC-13, ACC-20, INV-13, INV-28).
37. [V12-T9] THE System SHALL include Frontend component tests for round 2 within V12: the Sidebar Team members list shows the owner first with the "Owner" tag and no remove button on that row while the other rows keep theirs for the owner, Manager, and Admin; `MemberSearch` shows no owner row; the assignee popover lists the owner first; each pending row of the Invite modal shows Avatar_Image or Initials_Avatar, full name, Username, and Email; and no Inbox row or Sidebar member row renders an Email (ACC-19, INV-19, INV-27).
38. [V12-M1] THE System SHALL keep a manual verification checklist for the invite and join-request flow (design.md, "Manual verification checklist (V12 invite flow)", run by task 35.31) that uses two accounts and writes data on a local or scratch database only.
39. [V12-D1] THE System SHALL list "automated invite-flow end-to-end test" as a deferred item and SHALL schedule no data-writing Playwright test or Playwright project for the invite, join, or approve flow in V12; the E2E_Auth_Suite stays read-only (Requirement 1, criteria 65 to 72; AUTH-E2E-V12-08).
