# Boards, V12 changes

Requirement 22 (private-only access model) is new. Requirement 3 criteria listed below carry V12 labels.

### Requirement 22: Private-Only Board Access Model

**User Story:** As a Manager, I want every Board to be private and open only to its owner, its members, and staff, so that unrelated signed-in users never see work they were not invited to.

Note (V12, Decision Y): this requirement reverses Decision A (public Boards readable by every signed-in user), the Board `visibility` column, and Requirement 11 criteria 1 to 3, 6, 11, 12, and 13. Those criteria stay in this document with a "Superseded in V12" label so the history is readable. The local development database is reset by the V12 migration; nothing is backfilled.

#### Acceptance Criteria

1. [ACC-01] THE Backend SHALL treat every Board as private: THE Board table SHALL have no `visibility` column, no request body or query string SHALL accept a `visibility` field, no response SHALL contain one, and no Activity_Log row SHALL be written with the action `board.visibility_changed` (Decision Y).
2. [ACC-02] THE Backend SHALL grant Board_Access to a signed-in user on a non-soft-deleted Board exactly when the user is the Board_Owner, a BoardMember, a Manager, or an Admin (Decision Y).
3. [ACC-03] IF a signed-in user without Board_Access calls any Board-scoped route other than the routes under `/api/shared` and `/api/invite`, THEN THE Backend SHALL return HTTP 403 with an error Envelope, and IF no Token is present, THEN THE Backend SHALL return HTTP 401.
4. [ACC-04] WHEN a signed-in Member or Supervisor requests `GET /api/boards`, THE Backend SHALL return the non-soft-deleted Boards where the user is the Board_Owner or a BoardMember; WHEN a Manager or an Admin requests it, THE Backend SHALL return every non-soft-deleted Board (Decision Y).
5. [ACC-05] THE Backend SHALL never store a BoardMember row for a user whose role is `manager` or `admin`; IF `POST /api/boards/{id}/members` names such a user, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and `error.details.user_id` (Decision Y).
6. [ACC-06] WHEN an Admin changes a user's role to `manager` or `admin`, THE Backend SHALL delete that user's BoardMember rows and pending BoardJoinRequests in the same transaction and write one `board.member_removed` Activity_Log row per removed BoardMember (Decision Y).
7. [ACC-07] WHEN a Manager or an Admin calls `POST /api/boards/{id}/members` for a Member or Supervisor account that is not yet a BoardMember, THE Backend SHALL create the BoardMember, write one `board.member_added` Activity_Log row, and create one `board_added` Notification for that user in the same transaction (Decision Y; amends Requirement 3, criterion 11).
8. [ACC-08] IF a signed-in user whose role is `member` or `supervisor`, the Board_Owner included, calls `POST /api/boards/{id}/members` or `GET /api/boards/{id}/candidates`, THEN THE Backend SHALL return HTTP 403, or HTTP 401 when no Token is present (Decision Y; amends Requirement 3, criteria 12 and 25).
9. [ACC-09] WHEN a Manager or an Admin requests `GET /api/boards/{id}/candidates?search=<text>` with at least 2 characters after trimming, THE Backend SHALL return only users whose role is `member` or `supervisor`, who are neither the Board_Owner nor a BoardMember, under the V10 matching, ordering, 20-row limit, and fields (Requirement 3, criterion 25).
10. [ACC-10] WHEN the Board_Owner, a Manager, or an Admin calls `DELETE /api/boards/{id}/members/{user_id}`, THE Backend SHALL delete the BoardMember, clear `assignee_id` on every Card of that Board assigned to that user, write one `card.unassigned` Activity_Log row per cleared Card, and create no Notification, all in one transaction (Requirement 3, criterion 14, and Decision Y).
11. [ACC-11] WHEN a Card is assigned through `PATCH /api/cards/{id}` with a non-null `assignee_id`, THE Backend SHALL accept the value only when the user is the Board_Owner or a BoardMember of that Card's Board, and SHALL otherwise return HTTP 400 with the code `VALIDATION_ERROR` and `error.details.assignee_id` (Decision Y; amends Requirement 4, criterion 11).
12. [ACC-12] WHEN a Manager or an Admin reassigns a Board's `owner_id` to a Supervisor, THE Backend SHALL create one `board_added` Notification for the new owner in the same transaction, and SHALL clear `assignee_id` on Cards of that Board assigned to the previous owner unless the previous owner is a BoardMember, writing one `card.unassigned` row per cleared Card (Decision Y; amends Requirement 3, criterion 16).
13. [ACC-13] THE Backend SHALL return from `GET /api/boards/{id}/members` the Board_Owner (first, with `is_owner` true) and every BoardMember, each with `id`, `full_name`, `username`, `avatar_url`, and `is_owner`, listing a user once even when the Board_Owner is also a BoardMember, so that the assignee picker lists exactly the users who may be assigned (Decision Y; Open Question 23).
14. [ACC-14] THE Frontend SHALL render no visibility icon, no lock icon, no visibility toggle, and no visibility filter in the Sidebar Boards list, the Board header, the Home tiles, the new-board modal, or any Board edit form (Decision Y; amends Requirement 3, criteria 20, 22, 23, and 29).
15. [ACC-15] WHEN a signed-in Member or Supervisor has no Board, THE Frontend SHALL show on Home the message "You are not on any board yet. Ask a manager or a board owner for an invite link." and no list of other Boards (Decision Y).
16. [ACC-16] WHERE the viewer is a Manager or an Admin, THE Frontend SHALL show the add button in the Sidebar Team members heading, which opens the member search of Requirement 3, criteria 24 and 32, and SHALL show no add button to the Board_Owner or any other viewer (Decision Y; amends Requirement 3, criterion 24).
17. [ACC-17] WHEN the V12 migration runs and `APP_ENV` is `development` or `testing`, THE Backend SHALL drop `boards.visibility`, add `boards.invite_token`, create `board_join_requests`, alter `notifications` as Requirement 28 criterion 1 states, delete the rows of every user-referencing table as the V10 migration did, and print one line saying that local data was reset and that `flask seed-data` recreates it; IF `APP_ENV` has any other value, THEN THE migration SHALL abort before changing anything (Decision Y).
18. [ACC-18] WHEN `flask seed-data` runs, THE Backend SHALL create a Manager, an Admin, a Supervisor who owns a seeded Board, a second Supervisor, the Members `member` and `member2`, two seeded Boards (one with `member` and `member2` as BoardMembers, one without any Member), one seeded Card assigned to `member` with Subtasks, and no BoardMember row for the Manager or the Admin; running it twice SHALL create no duplicate (Decision Y; extends Requirement 1, criterion 64).
19. [ACC-19] THE Frontend SHALL list the Board_Owner first in the Sidebar Team members section, tagged "Owner", with the Avatar_Image or Initials_Avatar, the full name, and the Username and no Email, and SHALL show no remove button on that row to any viewer; WHERE the Board has no owner, THE Frontend SHALL show no owner row (Open Question 23; amends Requirement 3, criterion 24).
20. [ACC-20] IF `DELETE /api/boards/{id}/members/{user_id}` names the Board_Owner and the Board_Owner is not a BoardMember, THEN THE Backend SHALL return HTTP 404 with the code `NOT_FOUND` and change nothing (Open Question 22; the owner row of ACC-19 has no remove action, so the Frontend never sends this request for it).

### Requirement 3 criteria with V12 labels

Criteria of Requirement 3 that V12 changed. Each line is the full V1 to V11 criterion followed by its V12 label; the label wins.

9. THE Frontend SHALL list the Boards the viewer may see in the Sidebar and use that list as the Board switcher. (V12: the list is the Boards where the viewer is owner or Board_Member, and every Board for a Manager and an Admin; Requirement 22, criterion 4.)
11. WHEN the Board_Owner, a Manager, or an Admin adds a user to a Board through `POST /api/boards/{id}/members`, THE Backend SHALL create a BoardMember for that Board and user (Decision A). (V12, Decision Y: only a Manager or an Admin adds directly, and only Member and Supervisor accounts; the Board_Owner adds people through Join_Requests; Requirement 22, criteria 5, 7, and 8, and Requirement 24.)
12. IF an authenticated user who is not the Board_Owner, a Manager, or an Admin attempts to add or remove a BoardMember, THEN THE Backend SHALL return HTTP 403, or HTTP 401 when no Token is present (Decision A). (V12: adding is for a Manager or an Admin only; the Board_Owner, a Manager, and an Admin may still remove, Requirement 22, criterion 10.)
14. WHEN the Board_Owner, a Manager, or an Admin removes a BoardMember through `DELETE /api/boards/{id}/members/{user_id}`, THE Backend SHALL delete that BoardMember record (Decision A). (V12: the removal also clears the removed user's assignments on the Board, Requirement 22, criterion 10.)
16. WHEN a Manager or Admin reassigns a Board's `owner_id` to a user who has the supervisor role, THE Backend SHALL store the new `owner_id` (Decision 1). (V12: also notifies the new owner and clears the previous owner's assignments, Requirement 22, criterion 12.)
20. THE Frontend SHALL show each Board's visibility in the Sidebar Boards list and in the Board header as an icon with an accessible label and tooltip: a closed lock for `private` and an open lock for `public` (Decision I). **(Superseded in V12 by Requirement 22, criterion 14: no visibility icon exists; Home lists the Boards of Requirement 22, criterion 4.)**
22. WHEN a signed-in user opens Home, THE Frontend SHALL show a page at `/boards` that lists every Board the viewer may see, each with its visibility icon, and SHALL make Home the first Sidebar entry and the default destination after sign-in (Decision I). **(Superseded in V12 by Requirement 22, criterion 14: no visibility icon exists; Home lists the Boards of Requirement 22, criterion 4.)**
23. THE Frontend SHALL show the Board header in two rows: the first is the App_Header (Requirement 19) and holds the visibility icon and Board name and, for the Board_Owner, a Manager, or an Admin, the Share button (Requirement 18) on the left, and the Inbox bell and the User_Menu trigger on the right (reworded in V10); the second holds three bordered sections, progress ("12 of 18 done", the percent, and a thin bar) on the left, the Category filter chips in the middle as one strip that scrolls sideways with left and right arrow buttons shown only when more chips are hidden, and the search field on the right; the header SHALL have no Add Member button and no settings icon, and below 960 pixels the search field SHALL collapse to an icon that opens the search in a modal (Decision I). **(Amended in V12: the visibility icon is removed; the "Share" button is the "Public link" button for a Manager and an Admin only (Requirement 23, criterion 9); the "Invite" button is added for the Board_Owner, a Manager, and an Admin (Requirement 24, criterion 19).)**
24. THE Frontend SHALL keep one Team members section in the Sidebar, listing the Board's members, each with an Avatar_Image or Initials_Avatar (Decision U), with no separate Members navigation entry; WHERE the viewer is the Board_Owner, a Manager, or an Admin, the section heading SHALL carry an add button that opens a member search (a popover, or a modal when the viewport is too narrow) and each member SHALL carry a remove button that asks for confirmation (Decision I). **(Amended in V12 by Requirement 22, criterion 16: the add button is shown to a Manager and an Admin only. Amended in V12 round 2 by Requirement 22, criteria 19 and 20: the list starts with the Board_Owner, tagged "Owner", and the owner row carries no remove button.)**
25. WHEN the Board_Owner, a Manager, or an Admin requests `GET /api/boards/{id}/candidates?search=<text>` with a `search` of at least 2 characters after trimming, THE Backend SHALL return at most 20 users who are not yet BoardMembers of that Board, matched case-insensitively on `full_name`, on `username` by prefix, or on `email` by exact match only (never by prefix or substring), and ordered by name, each with `id`, `full_name`, `username`, `email`, and `avatar_url` (Decisions M, I, S, U, and W; reworded in V10 and again in rounds 2 and 3); IF `search` is missing or has fewer than 2 characters after trimming, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and an `error.details` entry for `search` and SHALL query no users; IF another signed-in user calls it, THEN THE Backend SHALL return HTTP 403, and with no Token HTTP 401 (Decision I). **(Amended in V12 by Requirement 22, criteria 8 and 9: Manager and Admin only, Member and Supervisor accounts only.)**
29. THE Frontend SHALL show each Board on Home as a plain bordered tile (no cover band or image) with the visibility icon and name, up to two lines of the description, a progress bar with the percent from `done_count` and `card_count`, the counts of Cards, Overdue_Cards, and members, and up to three member avatars followed by "+N" (Decision I). **(Superseded in V12 by Requirement 22, criterion 14: no visibility icon exists; Home lists the Boards of Requirement 22, criterion 4.)**
30. [EML-01] WHEN a signed-in user requests `GET /api/boards/{id}/members` without `include`, THE Backend SHALL return each member with `id`, `full_name`, `username`, and `avatar_url` and no `email`; WHEN the request carries `include=email` and the viewer has Board_Staff_Access, THE Backend SHALL add `email` to each member; IF the request carries `include=email` and the viewer lacks Board_Staff_Access, THEN THE Backend SHALL return HTTP 403, and with no Token HTTP 401 (Decision S). (V12: the response also carries the Board_Owner first and `is_owner`, Requirement 22, criterion 13.)
31. [EML-02] THE Frontend SHALL show a user's Email only in the candidate results of the member search (Board_Owner, Manager, Admin), in the assignee popover (Board_Staff_Access), and, from V12 round 2, in the pending join-request list of the Invite modal (Board_Owner, Manager, Admin; Requirement 24, criterion 13), and THE Backend SHALL return another user's Email in no other Board-scoped payload, including Comments, Activity_Log rows, Notifications, the Shared_View, the Sidebar member rows, and any list a Member can read (Decision S). A user's own Email in the `user` shape and the Admin user list are unchanged. (V12: the member search is for a Manager and an Admin only.)
