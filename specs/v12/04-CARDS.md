# Cards, V12 changes

Requirement 25 (Auto_Save) and Requirement 27 (Subtask permissions and derived progress) are new. Requirement 4 and 16 criteria listed below carry V12 labels.

### Requirement 25: Card Modal Auto-Save

**User Story:** As a user who edits a Card, I want every change to save by itself and to see that it saved, so that I never lose an edit and never have to remember a Save button.

Note (V12, Decision AB): this requirement supersedes the draft model of Decision I and Decision J's sentence "attachment changes in the card modal wait for Save changes". Requirement 4 criteria 21, 30, 32, 35, and 43 and the "one save, one Activity_Log row" rule are superseded and carry a label. The Backend API of `PATCH /api/cards/{id}` does not change; the Frontend sends smaller requests.

#### Acceptance Criteria

1. [SAVE-01] THE Frontend SHALL show no "Save changes" button and keep no draft of the Card in the Card modal; the footer holds only Archive (secondary) and Delete (danger, behind a `BaseConfirm` popover), right-aligned (Decision AB).
2. [SAVE-02] WHEN the title field loses focus or the user presses Enter in it, and the trimmed value differs from the last saved value, THE Frontend SHALL send one `PATCH /api/cards/{id}` with `{ "title": value }`; WHEN the description field loses focus or the user presses Ctrl+Enter or Cmd+Enter in it, and the value differs, THE Frontend SHALL send one `PATCH` with `{ "description": value }`.
3. [SAVE-03] IF the title is empty after trimming, THEN THE Frontend SHALL send no request, show the inline error "Title is required." beside the field, and keep the field focused for editing.
4. [SAVE-04] WHEN the user confirms a value in the category popover, the priority popover, or the assignee popover (choosing an option or Remove), THE Frontend SHALL send one `PATCH` with only that field (`category_id`, `priority`, or `assignee_id`) and close the popover.
5. [SAVE-05] WHEN the user closes the dates popover and the start date, the end date, or both differ from the last saved values, THE Frontend SHALL send one `PATCH` with `start_date` and `end_date`; WHILE the popover is open and the pair is invalid (Requirement 4, criterion 32), THE Frontend SHALL send nothing and show the inline error.
6. [SAVE-06] WHEN the user adds a Subtask, toggles it, renames it, reorders it, or deletes it, THE Frontend SHALL send that one call (`POST /api/cards/{id}/subtasks`, `PATCH /api/subtasks/{id}`, or `DELETE /api/subtasks/{id}`) at once, and WHEN the user adds an Attachment link or picks an Attachment file, THE Frontend SHALL send `POST /api/cards/{id}/attachments` at once (Decision AB; supersedes Requirement 4, criterion 43).
7. [SAVE-07] WHILE a field's request is in flight, THE Frontend SHALL show "Saving…" beside that field; WHEN it succeeds, THE Frontend SHALL show "Saved" for 2 seconds and then nothing; IF it fails, THEN THE Frontend SHALL show the server message (`error.details` first, otherwise `message`) as an inline error with a Retry button beside that field, keep the field editable with the user's text, and keep the last saved value as the comparison base.
8. [SAVE-08] THE Frontend SHALL announce each field's state through an `aria-live="polite"` region beside the field, so that "Saving", "Saved", and the error reach assistive technology.
9. [SAVE-09] WHEN the response of a field's `PATCH` arrives, THE Frontend SHALL merge into the displayed Card only the fields that request sent, so that a later response never overwrites another field the user is still editing (last write wins per field).
10. [SAVE-10] THE Backend SHALL apply concurrent edits as last write wins: it SHALL carry no version or ETag check on Cards in V12, and two users editing the same field produce two `card.updated` rows, the later value stands.
11. [SAVE-11] WHEN a `PATCH /api/cards/{id}` changes no value, THE Backend SHALL return HTTP 200 and write no Activity_Log row; WHEN it changes at least one value, THE Backend SHALL write exactly one `card.updated` row whose `metadata.changes` lists only the fields that changed, so that one save writes one row and, because the Frontend sends one field per request (the two dates together), the row reads as one change (Decision AB; replaces the "one save, one row" rule of Decision I).
12. [SAVE-12] WHEN a Subtask or Attachment is added, changed, or removed, THE Backend SHALL write one Activity_Log row in the same transaction with the action `card.subtask_added`, `card.subtask_updated` (toggle, rename, or reorder), `card.subtask_removed`, `card.attachment_added`, or `card.attachment_removed`, and with `metadata` holding `card_title` and the Subtask title or the Attachment name, and THE Frontend SHALL describe each as a sentence in `describeActivity` (Requirement 8, criteria 9 and 10).
13. [SAVE-13] WHEN the user closes the Card modal (header icon, Escape, or a click on the backdrop) while a field has a pending blur save or a request in flight, THE Frontend SHALL send the pending save, wait for every in-flight request to finish, and then close; WHILE it waits, THE Frontend SHALL show "Saving…" in the header.
14. [SAVE-14] IF the user closes the Card modal while a field is in the failed state of criterion 7, THEN THE Frontend SHALL ask in a `BaseConfirm` dialog "Some changes were not saved. Close anyway?" and close only on confirmation (replaces the "unsaved changes" prompt of Requirement 4, criterion 43).
15. [SAVE-15] THE Frontend SHALL keep the Comment composer independent of every field save, and a posted Comment SHALL appear in the thread without touching the state of any other field (Requirement 7).
16. [SAVE-16] WHERE the viewer has no edit right on the Card (Requirement 4, criteria 8 and 9, and every viewer of the Shared_View), THE Frontend SHALL render the fields read-only with no save state.

### Requirement 27: Subtask Permissions and Derived Progress

**User Story:** As a Member, I want to tick off the Subtasks of a Card assigned to me, and as any viewer I want the Card's progress to follow its Subtasks, so that the meter is never typed by hand and never out of date.

Note (V12, Decision AD): Requirement 4 criteria 12 to 14 already give the Assigned_Member the edit rights of a Subtask, so this decision does not reverse Decision 2; it states the exact matrix and makes the toggle an explicit, tested requirement. Reconciliation: the Card's `progress` was a stored, stretch column (Requirement 16, criterion 1) that no code writes yet; V12 makes it a computed, read-only field.

#### Acceptance Criteria

1. [SUB-01] THE Backend SHALL apply this Subtask matrix, each action also requiring Board_Access: toggle `is_done`, add, rename, reorder, and delete are allowed to a Manager, an Admin, and a Supervisor with Board_Staff_Access on any Card of the Board, and to a Member only on a Card whose `assignee_id` is that Member; every other combination returns HTTP 403, or HTTP 401 with no Token (Decision AD; Requirement 4, criteria 12 to 14).
2. [SUB-02] WHEN an Assigned_Member calls `PATCH /api/subtasks/{id}` with `{ "is_done": true }` or `{ "is_done": false }`, THE Backend SHALL persist the value, write one `card.subtask_updated` row, and return the Subtask.
3. [SUB-03] IF a Member calls any Subtask endpoint for a Card whose `assignee_id` is not that Member or is null, THEN THE Backend SHALL return HTTP 403 and change nothing (Decision 2).
4. [SUB-04] THE Backend SHALL compute `progress` on every Card payload as `(20 * done + total) // (2 * total)` (rounded half up, an integer from 0 to 10) when `total` is greater than 0, and as null when the Card has no Subtasks, where `done` and `total` count the Card's Subtasks, and SHALL also return `subtask_done_count` and `subtask_total_count`, all from the already loaded Subtasks with no extra query.
5. [SUB-05] IF a request body contains `progress`, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and `error.details.progress`, because `progress` is derived (Decision AD; supersedes Requirement 16, criterion 1 for `progress`; `views_count` stays stored and stretch).
6. [SUB-06] WHERE a Card has at least one Subtask, THE Frontend SHALL show a progress meter with the text "done of total" on the board Card and in the Card modal's Subtasks card; WHERE a Card has none, THE Frontend SHALL show no meter on the board Card and the text "No subtasks yet" in the modal.
7. [SUB-07] WHEN a Subtask is toggled, added, or deleted, THE Frontend SHALL update the meter from the response without a reload.
8. [SUB-08] WHERE the viewer is a Member and the Card is assigned to that Member, THE Frontend SHALL show enabled Subtask checkboxes; WHERE the Card is assigned to someone else, THE Frontend SHALL show them disabled; in the Shared_View and for any viewer without Board_Access THE Frontend SHALL show them disabled and send no request (Requirement 23, criterion 7).
9. [SUB-09] THE Backend SHALL include `progress`, `subtask_done_count`, and `subtask_total_count` in the shared Card payload, which already carries Subtasks (Requirement 18, criterion 11).

### Requirement 4 criteria with V12 labels

Criteria of Requirement 4 that V12 changed. Each line is the full V1 to V11 criterion followed by its V12 label; the label wins.

11. WHEN a Supervisor, Manager, or Admin with Board_Staff_Access assigns a Card to a user, THE Backend SHALL set the Card's `assignee_id` and create an `assigned` Notification for that user in the same transaction. (V12: the assignee must be the Board_Owner or a Board_Member, Requirement 22, criterion 11.)
12. WHEN a user with edit rights on a Card (Board_Staff_Access for a Supervisor, Manager, or Admin; Board_Access as the Assigned_Member for a Member) adds a Subtask to that Card, THE Backend SHALL store the Subtask with a title, `is_done` defaulting to false, and a Float `order`. (V12: unchanged, and stated as the matrix of Requirement 27, criterion 1.)
13. WHEN a user with edit rights on a Card toggles a Subtask's `is_done` or reorders it, THE Backend SHALL persist the change through `PATCH /api/subtasks/{id}`, setting a Subtask dropped between two siblings to the average of their `order` values, the first position to `min_order - 1`, the last position to `max_order + 1`, an empty checklist's first Subtask to 1.0, and renumbering the whole checklist as 1.0, 2.0, ... in the same transaction when the gap between adjacent `order` values falls below 1e-6. (V12: unchanged, and stated as the matrix of Requirement 27, criterion 1.)
14. WHEN a user with edit rights on a Card (Board_Staff_Access for a Supervisor, Manager, or Admin; Board_Access as the Assigned_Member for a Member) deletes a Subtask, THE Backend SHALL remove the Subtask through `DELETE /api/subtasks/{id}`. (V12: unchanged, and stated as the matrix of Requirement 27, criterion 1.)
21. WHEN a user clicks Save changes in the modal footer, THE Frontend SHALL commit every pending change of the left pane, the Card fields in one `PATCH /api/cards/{id}` call followed by the staged Attachment additions and removals, without closing the modal and without affecting the Comment composer (Decision I). **(Superseded in V12 by Requirement 25, criteria 1 to 6: there is no Save changes button; every change saves by itself.)**
30. THE Frontend SHALL show a Card's category, Priority, dates, and assignee in the Card modal as chips (a coloured label pill for the category, a flag chip for the Priority, one chip for the date range with a red Overdue state, and an avatar with an add button for the assignee), each opening a popover that edits a draft, and SHALL send nothing until the user clicks Save changes (Decision I). **(Amended in V12 by Requirement 25: each chip popover saves its own field when its value is confirmed or closed; there is no draft.)**
32. THE Frontend SHALL NOT let a start date later than the end date be chosen: the calendar disables days before the start while the end date is picked, a typed pair with the start after the end shows an inline error and disables Save changes, moving the start past an existing end date clears the end date and shows a hint, and the same day for both is allowed (Decision I; the Backend rule is criterion 3). **(Amended in V12: there is no Save changes button to disable; an invalid pair sends nothing and shows the inline error, Requirement 25, criterion 5.)**
33. THE Frontend SHALL pick the assignee in a small popover with a search box, the Board's members (Avatar_Image or Initials_Avatar, full name, and Email, loaded through `GET /api/boards/{id}/members?include=email`), a single choice, and a Remove action, with the search box matching full name, Username, and Email case-insensitively, and SHALL hide the control from a Member, who may not assign (Decisions I and S; the Backend rule is criterion 11). (V12: the picker lists the Board_Owner first, tagged "Owner", and then the Board_Members, Requirement 22, criteria 13 and 19, and saves when a choice is made, Requirement 25, criterion 4.)
35. THE Frontend SHALL place every action of the Card modal in its footer, aligned to the right: Archive (secondary), Delete (danger), then Save changes (primary, last), SHALL ask for confirmation in a small confirmation popover before Delete takes effect, and SHALL offer no Close button in the footer: the modal closes through the header close icon and Escape (Decision I). **(Superseded in V12 by Requirement 25, criterion 1: the footer holds Archive and Delete only.)**
39. THE Frontend SHALL show in the Card modal header the Card's title and the Board's name separated by a vertical bar ("Card title | Board name"), SHALL update the title part as the user edits the title field before saving, SHALL show "Untitled card" when the title is empty, and SHALL show the Column's name as a badge beside it (Decision I). (V12: the title part follows the field as it is typed; saving happens on blur or Enter, Requirement 25, criterion 2.)
43. THE Frontend SHALL stage Attachment additions (links and picked files) and removals in the modal draft and apply them only on Save changes, uploading picked files at that moment; WHEN the user closes the modal with unsaved changes, THE Frontend SHALL ask whether to discard them (Decision I). **(Superseded in V12 by Requirement 25, criteria 6, 13, and 14: Attachments save at once and there is no "unsaved changes" prompt.)**
44. THE Frontend SHALL ask for confirmation in a small confirmation popover, with Cancel and a danger Delete, before deleting a Subtask, removing an Attachment, or deleting a Card (Decision I). **(Amended in V12 by Decision AC: removing an Attachment and deleting a Comment use the modal form of `BaseConfirm`; the other actions keep the popover, Requirement 26.)**

### Requirement 16 criteria with V12 labels

Criteria of Requirement 16 that V12 changed. Each line is the full V1 to V11 criterion followed by its V12 label; the label wins.

1. WHERE the stretch features are enabled, THE Backend SHALL store a nullable 0 to 10 integer `progress` and an integer `views_count` defaulting to 0 on Card. **(Amended in V12 by Decision AD: `progress` is no longer stored; only `views_count` stays a stretch column.)**
2. WHERE the stretch features are enabled, THE Frontend SHALL show the per-card progress meter, views counter, and the decorative Overview, Notes, and Questions tabs as in the prototype. **(Amended in V12: the progress meter is derived from Subtasks and is not stretch, Requirement 27; the views counter and the decorative tabs stay stretch.)**
