# Requirements Document: V10 changes

## Introduction

Version V10 revises V9. It reverses part of Requirement 11 (Guests no longer browse public Boards; Decision K), replaces `login_identifier` with a separate Username and Email (Decisions M and N, breaking), brings rate limiting into scope (Decision O, breaking for the error shape), adds the App_Header with the User_Menu and the Profile_Page (Decision L), and guards every signed-in page (Decision P). **Round 2 within V10** (still V10, not V11; V10 is specified but not implemented) defers registration rate limiting (Decision Q), replaces the avatar URL with an uploaded Avatar_Image (Decision R), shows the Email to staff in the candidate search and the assignee popover (Decision S), and sends an invalid Token to `/login` on every request (Decision T). Earlier domain files stay as they were; this folder holds only the domains that changed.

## Glossary (new and changed terms)

- **Guest**: A visitor without an account or Token. Can open a Board only through a Share_Link (Decision K) and sees its columns and cards read-only, never its comments or activity. A Guest cannot list or browse Boards.
- **login_identifier**: The single unique string column on User that Decision C introduced. Removed in V10 (Decision M); it survives only as a historical term in the V2 to V9 snapshots and in the downgrade of the migration.
- **Username**: The User's unique, case-insensitive handle, 3 to 30 characters from `a-z`, `0-9`, `_`, and `.`, stored in lowercase (Decision M).
- **Email**: The User's unique, case-insensitive email address, valid format, at most 255 characters, stored in lowercase. Required on every account: the V10 migration resets local development data, so no account lacks one (Decisions M and V).
- **Identifier**: The single login form value, either a Username or an Email, sent as the request field `identifier` (Decision N). It is treated as an Email only when it contains `@`.
- **Board**: A project container holding Columns, Cards, and Categories. Has `visibility` (`public` or `private`), a nullable `owner_id`, and a nullable `share_token`.
- **Share_Token**: The random, unguessable, unique string stored in `Board.share_token` (at least 256 bits from a cryptographically secure source). A null value means sharing is off (Decision K).
- **Share_Link**: The URL `/shared/{token}` built from a Board's Share_Token. Opens the Shared_View without sign-in (Decision K).
- **Shared_View**: The read-only Frontend view at `/shared/{token}` of a Board's Columns, Cards, Card details, Categories, and Attachment links, without Comments, Activity, Inbox, or any write action (Decision K).
- **Board_Access**: A signed-in user has Board_Access to a Board when the Board is public (every signed-in user, Decision A), or the user is its Board_Owner, a BoardMember, a Manager, or an Admin. For a private Board, a Supervisor has Board_Access only as owner or BoardMember, and a Member only as BoardMember. A Guest never has Board_Access; a Share_Token grants only the Shared_View of Requirement 18. Card, Comment, Attachment, Activity_Log, and Category access always resolves through the owning Board's Board_Access.
- **Sidebar**: The left navigation holding brand, nav (including Inbox, Activity, and Categories where permitted), the Boards list, and team members. It holds no profile entry and no Log out item (Decision L).
- **App_Header**: The persistent top bar of every Protected_Route page: the Sidebar toggle below 960 pixels, the page context (on a Board, the visibility icon, name, and Share button), the Inbox bell, and the User_Menu trigger (Decision L).
- **User_Menu**: The menu opened from the user icon in the App_Header, holding Profile above Log out (Decision L).
- **Profile_Page**: The Protected_Route `/profile` where the signed-in user edits full name and avatar, sees Username and Email, and changes the password (Decision L).
- **Avatar_Image**: The PNG, JPEG, or WebP picture a user uploads on the Profile_Page, at most 2 MB, stored under a generated file name (Decision R).
- **Avatar_URL**: The value of `avatar_url` in a `user` payload, and of `author_avatar_url`, `avatar_url`, and `assignee_avatar_url` in the Comment, Board member, candidate, and Card payloads of Decision U: a Signed_File_URL for the Avatar_Image, or null when the user has none (Decisions R and U).
- **Initials_Avatar**: The fallback avatar that shows the initials of the user's full name when there is no Avatar_URL or the image fails to load (Decision R). The initials are the first letter of each of the first two words of `full_name`, upper-cased; a one-word name gives one letter and a blank name gives `?` (Decision U).
- **Rate_Limiter**: The Backend component that counts attempts in the `rate_limit_attempts` Postgres table and blocks further attempts with HTTP 429 `RATE_LIMITED` (Decision O).
- **Rate_Limit_Window**: The sliding period, 900 seconds by default, over which the Rate_Limiter counts attempts (Decision O).
- **Client_IP**: The client address the Rate_Limiter keys on: the connection's remote address, or the address from `X-Forwarded-For` only through the number of trusted proxies configured in `TRUSTED_PROXY_COUNT` (Decision O).
- **Test_Account**: A seeded, existing user whose Username or Email and password are supplied to the E2E_Auth_Suite through the environment variables `E2E_USER_IDENTIFIER` and `E2E_USER_PASSWORD` (the variable names are unchanged from V9). The suite assumes a Member account and never creates, edits, or deletes accounts (V9). The suite makes at most one failed login attempt against this account per run (AUTH-E2E-SI-06), far below the lockout threshold, and each successful sign-in resets the pair counter.
- **Throwaway_Identifier**: A Username-shaped value generated per test run (`e2e-rl-` plus random lowercase characters) that belongs to no account. The rate-limit test (AUTH-E2E-SI-11) fails logins against it, so the Test_Account is never locked and no account is created (V10; see Decision O).
- **User_Menu_Trigger**: The App_Header button with the accessible name "User menu". It is visible exactly while a user is signed in, so the E2E_Auth_Suite uses it as the signed-in indicator (V10).
- **Sign_Out_Control**: The "Log out" menu item of the User_Menu. It is the only sign-out control in the Frontend (Decision L, resolving Open Question 6).
- **Generic_Login_Error**: The form-level message "Invalid credentials" that the Backend returns for both an unknown Identifier and a wrong password (`auth_service.login`).
- **Protected_Route**: A Frontend page that requires a Session_Cookie and redirects a visitor without one to `/login`. Every page under the `(app)` route group is one: `/boards`, `/boards/{id}` and its sub-pages, `/profile`, and `/admin/users` (Decision P, resolving Open Question 5). `/login`, `/register`, and `/shared/{token}` are not.
- **Safe_Return_Path**: The value of the `next` query parameter on `/login` when it is a path and query that starts with a single `/`, does not start with `//` or `/\`, has no control character, has at most 512 characters, and starts with `/boards`, `/profile`, or `/admin`; any other value is ignored (Decision T).

## Open Questions (resolved, changed, and new in V10; 7, 8, 10, and 12 resolved and 14 to 16 added in round 2)

1. **login_identifier format validation (RESOLVED in V10, Decision M):** `login_identifier` no longer exists. Username and Email each have a defined format (Requirement 1, criteria 47 and 48). The V2 provisional behaviour is withdrawn.
3. **Decision A interpretation (RESOLVED in V10):** Public Boards stay readable by every signed-in user. Decision K restates this and removes only the Guest half.
5. **Route guard (RESOLVED in V10, Decision P):** every page under the `(app)` route group is a Protected_Route, guarded by `frontend/proxy.ts`. Criteria 1.31 and 1.33 are no longer pending, and their tests are no longer `test.fixme`.
6. **Sign-out control location (RESOLVED in V10, Decision L):** sign-out is the "Log out" item of the User_Menu in the App_Header; the Sidebar no longer has it.
7. **Invalid Token on a server render (RESOLVED in V10 round 2, Decision T; originally V9):** the redirect and the cookie removal are specified in Requirement 1, criteria 55 to 62. The original question:  `lib/api.ts` redirects to `/login` on a 401 only for client-side calls made while a Session_Cookie is present. Whether a server render (`serverGet`) of a Protected_Route with an invalid or expired Session_Cookie redirects, shows an error, or fails is not specified; `frontend/proxy.ts` checks only that the cookie exists. Recommendation: redirect to `/login` on a 401 from a server render (the stale cookie is overwritten by the next sign-in). Criterion 1.34 covers the client-side call only.
8. **Rate-limit thresholds for register and availability (RESOLVED for register in V10 round 2, Decision Q):** registration is not rate limited. The availability threshold of 60 is still a proposal and is Open Question 14.
9. **Change-password brute force (RESOLVED in V10 round 3, Decision W):** `POST /api/auth/change-password` is rate limited under its own scope (Requirement 20, criteria 19 to 23). The original question: the endpoint takes the current password but was not covered by the Rate_Limiter in V10, because Decision O named login, register, and availability only.
10. **Avatar editing method (RESOLVED in V10 round 2, Decision R):** the user uploads an image (PNG, JPEG, or WebP, at most 2 MB) on the Profile_Page; the `https` URL rule is withdrawn (Requirement 19, criteria 18 to 33).
11. **Legacy accounts with identifiers that fit neither shape (RESOLVED in V10 round 3, Decision V):** the application is not deployed and the only data is on a local development machine, so the migration resets that data and re-seeding recreates it; there is no backfill, no sanitized Username, and no Email_Prompt (Requirement 1, criteria 52, 53, 63, and 64).
12. **Candidate search by name (RESOLVED in V10 round 2, Decision S):** name matching stays, and the candidate response and the assignee popover show the Email to staff. Open Question 16 records the exposure this creates.
13. **Shared_View scope details (RESOLVED in V10 round 3, Decision W):** the Shared_View shows the assignee's `full_name` only (Requirement 18, criteria 11 and 25), never Username, Email, or Avatar_URL, and accepts `search` and `filter[...]` on the shared Card list as written. Consistency note: the shared Card payload keeps the opaque `assignee_id` that the Card list already carries, which is why `filter[assignee]` is accepted, but a Guest has no member list, so the shared filter row offers search and Category only.

14. **Availability limiter kept (RESOLVED in V10 round 3, Decision W):** the limiter on `GET /api/auth/availability` stays at 60 per Client_IP per window, and registration stays unlimited (Decision Q). Because `POST /api/auth/register` answers the same question with a 409, an attacker can still enumerate Usernames and Emails through it; this is a recorded, accepted gap for V10, to be revisited together with registration limiting.
15. **Avatar visibility (RESOLVED in V10 round 3, Decision U):** `avatar_url` is also returned for Comment and Reply authors, Board members, candidates, and Card assignees, to signed-in viewers only; Guests on a Share_Link see initials (Requirement 19, criteria 34 to 40).
16. **Email exposure through candidate search (RESOLVED in V10 round 3, Decision W):** the search needs at least 2 characters after trimming (Requirement 3, criterion 25). Email only for Manager and Admin and a per-user request limit were not chosen; a Board_Owner can still read the Email of an account whose name matches a 2-character search, which is the accepted residue of Decision S.
17. **Avatar URL cache churn (RESOLVED in V10 round 3, Decision W):** every response signs a fresh `avatar_url` (Decision R), so a browser refetches avatar images when a board, comment list, or member list is loaded.
