### Requirement 19: App Header, User Menu, and Profile

**User Story:** As a signed-in user, I want one header on every page with my account menu, so that I can reach my profile and sign out from the same place.

#### Acceptance Criteria
**Round 3 within V10 (Decisions U to W):** criteria 11, 12, 16, and 26 reworded; 13 and 14 withdrawn (no Email_Prompt); avatar routes moved to `/api/users`; 34 to 40 added (avatars in Comments, member lists, candidates, and Card assignees; initials rule).

New in V10 (Decisions L and M). Criteria 1 to 17 are new in V10; criteria 8, 9, and 10 are reworded and criteria 18 to 33 (avatar upload) are added in round 2 within V10 (Decision R, resolving Open Question 10).

1. [HDR-01] THE Frontend SHALL render the App_Header on every Protected_Route page, fixed at the top, so that the same header serves Home, a Board, the Categories and member screens, the Profile_Page, and the admin screens (Decision L).
2. [HDR-02] THE Frontend SHALL show in the App_Header a User_Menu_Trigger (a user icon, or the avatar when `avatar_url` is set) with the accessible name "User menu", and WHEN the user activates it, THE Frontend SHALL open a menu whose items are, in order, Profile and then Log out (Decision L).
3. [HDR-03] WHEN the user activates Profile, THE Frontend SHALL navigate to `/profile` and close the menu.
4. [HDR-04] WHEN the user activates Log out, THE Frontend SHALL call `POST /api/auth/logout`, discard the Token and the Session_Cookie whether the call succeeds or fails, and navigate to `/login` (criteria 15 and 16 of Requirement 1).
5. [HDR-05] THE Frontend SHALL show no Log out item and no profile entry in the Sidebar (Decision L).
6. [HDR-06] THE Frontend SHALL build the User_Menu with `BaseMenu`, so that it opens and closes with the keyboard, closes on Escape and returns focus to the trigger, and shows the focus ring of Requirement 14, criterion 15.
7. [HDR-07] WHILE the viewport is below 960 pixels, THE Frontend SHALL keep the User_Menu_Trigger in the persistent header (Requirement 14, criterion 8).
8. [PROF-01] WHEN a signed-in user opens `/profile`, THE Frontend SHALL show the full name as an editable field, the avatar section of criterion 28, the Username and the Email as read-only text, and a change-password form with Current password and New password fields, loading them from `GET /api/auth/me`.
9. [PROF-02] WHEN a signed-in user calls `PATCH /api/auth/me` with `full_name`, THE Backend SHALL apply the change and return the `user` shape of Requirement 1, criterion 1.
10. [PROF-03] THE Backend SHALL accept `full_name` only when it is non-blank after trimming and at most 255 characters; the avatar changes only through criteria 18 to 27 (Decision R, which withdraws the `https` URL rule of V10); otherwise THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and an `error.details` entry for the field.
11. [PROF-04] IF a `PATCH /api/auth/me` body contains `username`, `email`, `role`, `avatar_url`, or any other field the endpoint does not define, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and change nothing (Decision V: `email` is no longer editable here).
12. [PROF-05] WHEN a signed-in user calls `POST /api/auth/change-password` with `current_password` and `new_password` of at least 8 characters and the user is not blocked by criteria 19 to 23 of Requirement 20, THE Backend SHALL verify the current password, store the new hash, return HTTP 200 with the message "Password changed", and leave the issued Token valid until its expiry (Requirement 1, criterion 14).
13. [PROF-06] [Withdrawn in V10 round 3, Decision V] No account has a null Email, so there is no Email_Prompt and `PATCH /api/auth/me` does not accept an Email. The ID stays so that references do not move.
14. [PROF-07] [Withdrawn in V10 round 3, Decision V] The Email is no longer saved from the Profile_Page, so the `CONFLICT` on an Email save no longer exists there. The ID stays so that references do not move.
15. [PROF-08] WHEN a profile change or a password change succeeds, THE Backend SHALL write one Activity_Log row (`user.profile_updated` or `user.password_changed`, target type `user`) in the same transaction, with no password, hash, or Token in `metadata`.
16. [PROF-09] IF `current_password` does not match the stored password, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and an `error.details` entry for `current_password`, count one failed attempt for the user in the Rate_Limiter (Requirement 20, criterion 20), and never return HTTP 401, because a 401 makes the Frontend discard the session (Requirement 13, criterion 10); IF the user is blocked, THEN THE Backend SHALL return HTTP 429 `RATE_LIMITED` (Requirement 20, criterion 19) and the Frontend SHALL keep the session.
17. [PROF-10] THE Frontend SHALL validate `new_password` for at least 8 characters and `current_password` for a non-empty value before sending, and SHALL map `error.details` onto the matching fields.

**Avatar upload (V10 round 2, Decision R)**
18. [AVT-01] WHEN a signed-in user calls `POST /api/users/me/avatar` as `multipart/form-data` with one file part named `file`, THE Backend SHALL store the image as that user's Avatar_Image and return HTTP 200 with message "Avatar updated" and the `user` shape of Requirement 1, criterion 1.
19. [AVT-02] THE Backend SHALL accept an upload only when its leading bytes identify PNG (`89 50 4E 47 0D 0A 1A 0A`), JPEG (`FF D8 FF`), or WebP (`RIFF`, four size bytes, then `WEBP`), and SHALL ignore the file extension and the client's Content-Type for that decision; otherwise THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and an `error.details` entry for `file`.
20. [AVT-03] IF an upload is empty or larger than 2,097,152 bytes, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and an `error.details` entry for `file`, SHALL read at most 2,097,153 bytes of the part, and SHALL store nothing.
21. [AVT-04] THE Backend SHALL store the Avatar_Image as `UPLOAD_DIR/avatars/<32 hexadecimal characters>.<png|jpg|webp>`, where the name is random and the extension comes from the detected type, and SHALL NOT use, store, or log the original file name, and SHALL record only that generated name in `User.avatar_path`.
22. [AVT-05] WHEN an upload replaces an existing Avatar_Image, THE Backend SHALL delete the previous file after the database change commits; IF that deletion fails, THEN THE Backend SHALL log the failure without the user's data and still return success; IF the database change fails, THEN THE Backend SHALL delete the file it just wrote.
23. [AVT-06] WHEN a signed-in user calls `DELETE /api/users/me/avatar`, THE Backend SHALL set `avatar_path` to null, delete the file after the commit, and return HTTP 200 with message "Avatar removed" and the `user` shape with `avatar_url` null; WHEN the user has no Avatar_Image, THE Backend SHALL return the same response and change nothing.
24. [AVT-07] THE Backend SHALL return `avatar_url` in every `user` payload (register, login, `GET` and `PATCH /api/auth/me`, and the Admin user endpoints) as a Signed_File_URL `/api/users/{user_id}/avatar/file?exp=<unix>&sig=<hex>` valid for 15 minutes, produced by the signing function of Decision D with the scope `avatar` so that an avatar signature never opens an Attachment file, or as null when the user has no Avatar_Image; THE Backend SHALL create the URL only while building a response to a request that has authenticated.
25. [AVT-08] WHEN a request reaches `GET /api/users/{user_id}/avatar/file` with a valid, unexpired signature for that user, THE Backend SHALL return the stored bytes with the Content-Type of the detected type, `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`, and `Cache-Control: private, max-age=300`; IF the signature is missing, modified, or expired, THEN THE Backend SHALL return HTTP 403 with the error Envelope; IF the user has no Avatar_Image, THEN THE Backend SHALL return HTTP 404. The route takes no Token, because an `<img>` request cannot send one (the trade-off of Decision D).
26. [AVT-09] THE Backend SHALL include an Avatar_URL only in the `user` shapes of criterion 24 and in the payloads of criterion 34 (Comment and Reply authors, Board members, candidates, Card assignees), and in no other payload: Notifications, Activity_Log rows, and every shared route carry none, and a Guest on a Share_Link sees initials only (Decision U, resolving Open Question 15).
27. [AVT-10] IF a `PATCH /api/auth/me` body or an Admin `POST /api/users` or `PATCH /api/users/{id}` body contains `avatar_url`, THEN THE Backend SHALL return HTTP 400 with the code `VALIDATION_ERROR` and change nothing (Decision R; breaking for the Admin endpoints).
28. [AVT-11] THE Frontend SHALL show on the Profile_Page an avatar section with the current Avatar_Image or the Initials_Avatar, a "Choose image" button that opens a file picker limited to PNG, JPEG, and WebP, a preview of the chosen file before it is sent, an Upload button (primary) and a Cancel button (secondary) while a file is chosen, and, only while an Avatar_Image exists, a Remove button (danger) that asks for confirmation through `BaseConfirm`.
29. [AVT-12] IF the chosen file is not PNG, JPEG, or WebP by its declared type, or is larger than 2 MB, THEN THE Frontend SHALL show "Use a PNG, JPEG, or WebP image." or "The image must be 2 MB or smaller." beside the picker and send no request; WHEN the Backend returns an `error.details.file` message, THE Frontend SHALL show it there, and on a network failure THE Frontend SHALL show a retry message and keep the chosen file.
30. [AVT-13] WHILE `avatar_url` is null, THE Frontend SHALL show the Initials_Avatar; IF an avatar image fails to load, THEN THE Frontend SHALL request `GET /api/auth/me` once for a fresh URL, retry once, and then show the Initials_Avatar.
31. [AVT-14] WHEN an upload or a removal succeeds, THE Frontend SHALL update the avatar in the Profile_Page, the User_Menu_Trigger, and the stored user without a page reload, and SHALL show a success message.
32. [AVT-15] WHEN an upload or a removal succeeds, THE Backend SHALL write one Activity_Log row `user.profile_updated` with target type `user` and `metadata` `{ "fields": ["avatar"] }` in the same transaction, with no file name, path, or URL in `metadata` (criterion 15).
33. [AVT-16] IF `POST` or `DELETE /api/users/me/avatar` carries no Token, THEN THE Backend SHALL return HTTP 401; WHEN two uploads for the same user run at the same time, THE Backend SHALL serialize them on the user row so that exactly one Avatar_Image file remains for that user.

**Avatars in viewer-facing payloads (V10 round 3, Decision U)**

34. [AVT-17] THE Backend SHALL add an Avatar_URL, or null when the user has no Avatar_Image, as `author_avatar_url` on every Comment and Reply, as `avatar_url` on every row of `GET /api/boards/{id}/members` (with or without `include=email`) and of `GET /api/boards/{id}/candidates`, and as `assignee_avatar_url`, together with `assignee_name`, on every Card returned by `GET /api/boards/{id}/cards`, `GET /api/cards/{id}`, and the Card create, update, move, and assign responses (null for both when the Card has no assignee).
35. [AVT-18] THE Backend SHALL build each of those URLs with the signing of criterion 24 (scope `avatar`, 15 minutes), only while building a response to a request that has authenticated, and SHALL add no Email to any of those payloads beyond the places Decision S allows.
36. [AVT-19] THE Backend SHALL read the author and assignee names and avatar paths in the existing batched lookups (one query for all authors or assignees of a response), declare no new model relationship, trigger no lazy load, and sign each distinct user once per response, so that the query count does not depend on the number of distinct authors or assignees (Requirement 14, criterion 12; Decisions F and U).
37. [AVT-20] THE Backend SHALL leave every shared route without an Avatar_URL and THE Frontend SHALL show the Initials_Avatar for the assignee in the Shared_View, because a share-scoped avatar URL needs its own signature scope, a new shared field, and a file-route branch for a status-only view (Decisions K and U).
38. [AVT-21] THE Frontend SHALL draw every user avatar through `BaseAvatar`, showing the Avatar_Image when the URL is set and the Initials_Avatar otherwise, for the author of each Comment and Reply, each Team members row of the Sidebar, each member search result, each row of the assignee popover, the assignee on a board Card, the assignee chip of the Card modal, and the member avatars of a Home tile (Decision U).
39. [AVT-22] THE Frontend SHALL compute the Initials_Avatar from `full_name` as the first letter of each of the first two words, upper-cased, one letter for a one-word name, and `?` for a blank name, and SHALL show it when the URL is null or the image fails after the one refresh of criterion 30 (Decision U).
40. [AVT-23] THE Frontend SHALL show no Email in any avatar tooltip, `alt` text, or label; `BaseAvatar` takes the full name as its tooltip and `alt` text (Decisions S and U).
