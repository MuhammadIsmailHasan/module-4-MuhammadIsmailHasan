### Requirement 15: Automated Testing

**User Story:** As a developer, I want automated tests for the API and the main user journey, so that regressions are caught.

#### Acceptance Criteria
**Round 3 within V10 (Decisions U to W):** criteria 16, 18, and 24 reworded; 25 to 27 added (avatars in payloads, avatar components, seed).

V10 changes: criteria 7, 11, and 15 reworded; criteria 16 to 19 added (Rate_Limiter, share-link, migration tests, and the rate-limit E2E rule). Criteria 1 to 6, 8 to 10, 12 to 14 are unchanged from V9. **Round 2 within V10:** criterion 16 reworded (no registration limit; Decision Q); criteria 20 to 24 added (avatar API and component tests, no avatar e2e, route guard and return-path tests, Email exposure tests).

7. THE System SHALL include `pytest` tests for Attachment access covering a permitted viewer, an unrelated Member, a Guest (HTTP 401 on the authenticated route), and an expired signature (Decision D; reworded in V10).
11. THE E2E_Auth_Suite SHALL read the base URL from `E2E_BASE_URL`, the Test_Account's Username or Email from `E2E_USER_IDENTIFIER`, and its password from `E2E_USER_PASSWORD` (the Username or Email of the Test_Account in V10), and SHALL contain no credential literal (V9).
15. THE E2E_Auth_Suite SHALL start every test in a fresh browser context with no Session_Cookie, SHALL create no account or other data, and SHALL leave the Test_Account unchanged (V9). The only rows the suite causes are Rate_Limiter attempt rows for a Throwaway_Identifier, which the Rate_Limiter deletes when they age out of the window (V10).
16. THE System SHALL include `pytest` tests for the Rate_Limiter that use a fake clock and small thresholds passed through the app factory, covering the block at the threshold, the reset on success, the per-IP limit, the window expiry, the `Retry-After` value, two workers sharing the same table, that `POST /api/auth/register` is never answered with 429 however many requests one Client_IP makes, and the `change_password` scope (block at the threshold per user, reset on success, independent per user, no password comparison while blocked) (Requirement 20; Decisions Q and W; V10).
17. THE System SHALL include `pytest` tests that a Share_Token stops working immediately after disable or regenerate, that no shared response contains `comments`, `activity`, or `activity_log`, and that a Signed_File_URL issued through a Share_Token stops working after disable or regenerate (Requirement 18; V10).
18. THE System SHALL include `pytest` tests for unique case-insensitive `username` and `email` and for the V10 migration reset of criterion 63 of Requirement 1 (the abort when `APP_ENV` is not `development` or `testing`, the empty user tables and the NOT NULL columns after `upgrade`, and a working `downgrade`) (Decisions M and V; V10, reworded in round 3).
19. THE E2E_Auth_Suite SHALL read nothing about the rate-limit thresholds from the Backend: the rate-limit test SHALL keep submitting wrong passwords for a Throwaway_Identifier until the form shows the wait time, up to 10 attempts, and SHALL fail with a message naming `RATE_LIMIT_LOGIN_PAIR_MAX` if no block appears (V10).

20. THE System SHALL include `pytest` API tests for the avatar endpoints. Happy cases: a PNG, a JPEG, and a WebP are each accepted and the returned Avatar_URL serves the same bytes with the matching Content-Type; a file named `x.txt` that holds PNG bytes is accepted, and the stored name is a generated name with the detected extension; replacing deletes the previous file and `DELETE` deletes the current one and succeeds when there is none; a user without an avatar has `avatar_url` null. Negative cases: no Token returns 401; a text file named `x.png`, an SVG, a GIF, and an empty file return 400 with `details.file`; a file of 2,097,153 bytes returns 400 and one of 2,097,152 bytes is accepted; a missing `file` part returns 400; a file name such as `../../x.png` leaves no file outside `UPLOAD_DIR/avatars/`; a bad, modified, or expired signature returns 403; a signature for one user does not open another user's file; a user without an avatar returns 404 from the file route; `PATCH /api/auth/me` with `avatar_url` returns 400; no shared route response contains `avatar_url` (Decision R; V10 round 2).
21. THE System SHALL include Frontend component tests for the Profile avatar section covering the preview after choosing a file, the Upload and Remove actions (Remove behind `BaseConfirm`), the wrong-type message, the too-large message, a server `details.file` message, and the Initials_Avatar fallback with one refresh of the URL on an image load error (Decision R; V10 round 2).
22. THE E2E_Auth_Suite SHALL contain no avatar test, because uploading changes account data and criterion 15 forbids that; avatar behaviour is verified by criteria 20 and 21 and by a manual smoke check before release (upload, preview, replace, remove) (V10 round 2).
23. THE System SHALL include `vitest` tests for `frontend/proxy.ts` (no cookie, malformed cookie, `exp` in the past, a valid unexpired cookie, cookie removal on the redirect, and the public paths untouched) and for the Safe_Return_Path rule (`/boards`, `/boards?x=1`, `//evil.com`, `/\evil.com`, `https://evil.com`, `/other`, and a 513-character path), and `pytest` tests that a malformed or expired Bearer Token on a shared route is answered as a Guest with 200 (Decision T; V10 round 2).
24. THE System SHALL include `pytest` tests that the candidate response carries `email` for the Board_Owner, a Manager, and an Admin and returns 403 for other signed-in users, that `GET /api/boards/{id}/members` has no `email` key by default and returns 403 for `include=email` from a Member, that no Comment, Activity_Log, Notification, shared, or default member response body contains another user's Email, and that a candidate search of 0 or 1 characters after trimming returns 400 with `details.search` while 2 characters are accepted (Decisions S and W; V10 rounds 2 and 3).
25. THE System SHALL include `pytest` tests that `author_avatar_url`, `avatar_url`, and `assignee_avatar_url` of Requirement 19, criterion 34, are signed URLs that open the right bytes and are null for a user without an Avatar_Image; that the same fields are absent from every shared route, Activity_Log row, and Notification body; that no Email appears in the Comment, member (default), shared, activity, or Notification bodies; and that the query count of the Comment list and of the Card list is the same for 5 and for 50 distinct authors or assignees (Decision U; V10 round 3).
26. THE System SHALL include Frontend component tests that `BaseAvatar` shows the Avatar_Image when the URL is set and the Initials_Avatar of Requirement 19, criterion 39 when it is null or fails twice, and that `CommentThread`, the Sidebar Team members, `MemberSearch`, `MemberPicker`, the board Card, and the Card modal assignee chip render it (Decision U; V10 round 3).
27. THE System SHALL include `pytest` tests that `flask seed-users` and `flask seed-data` give every seeded user a Username, an Email, and a full name, that the Test_Account `member` can log in with its Username and with its Email, and that a second run creates no duplicate (Requirement 1, criterion 64; Decision V; V10 round 3).
